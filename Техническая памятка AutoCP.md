# Техническая памятка AutoCP

## 1. Назначение памятки

Этот документ фиксирует технические детали сервиса AutoCP, которые не обязательно включать в основной управленческий документ, но важно сохранить для дальнейшей поддержки, настройки и восстановления контекста по проекту.

## 2. Основные файлы проекта

Ключевые файлы и каталоги:

- `backend/app.py` - основной FastAPI backend, API, интеграция с Битрикс24, DaData, ИИ, фоновые задачи;
- `frontend/index.html` - структура веб-интерфейса;
- `frontend/app.js` - логика интерфейса, запросы к API, опрос статусов задач;
- `frontend/styles.css` - стили интерфейса;
- `mainprompt.md` - промпт финального выбора материалов для ИИ;
- `build_payload_new.py` - подготовка payload для презентации;
- `build_presentation_direct_new.py` - сборка PPTX по шаблону;
- `build_pdf_direct.py` - генерация HTML/PDF-варианта;
- `build_pdf_template_direct.py` - генерация PDF напрямую по PDF-шаблону;
- `templates/pdf_presentation.html` и `templates/pdf_presentation.css` - шаблоны HTML/PDF;
- `data_sources.json` - источники скачивания Excel-справочников;
- `bitrix_config.json` - рабочая конфигурация полей Битрикс24;
- `bitrix_config.example.json` - пример маппинга полей;
- `ai_config.json` - рабочая конфигурация ИИ-провайдеров;
- `ai_config.example.json` - пример конфигурации ИИ;
- `.env` и `.env.example` - переменные окружения;
- `data/presentation_jobs` - сохраненные состояния задач сборки;
- `data/presentation_audit.jsonl` - журнал результатов сборок.

## 3. Backend

Backend реализован в `backend/app.py` на FastAPI. При старте приложение:

- загружает `.env`;
- настраивает пути к локальным файлам и каталогам;
- монтирует статические файлы frontend;
- при необходимости скачивает исходные XLSX-файлы из `data_sources.json`.

Основные глобальные структуры:

- `PRESENTATION_JOBS` - задачи сборки презентаций в памяти;
- `PRESENTATION_JOBS_DIR` - каталог для сохранения задач на диск;
- `PRESENTATION_AUDIT_FILE` - JSONL-журнал сборок;
- `AI_SELECTIONS` - временное хранилище подготовленных выборов материалов;
- `BITRIX_JOBS` - задачи, запущенные из Битрикс24.

Для потокобезопасности используются `threading.Lock`.

## 4. Frontend

Frontend - статический HTML/JS/CSS без отдельного фреймворка. Интерфейс обращается к FastAPI через `fetch`.

Основные действия frontend:

- загрузка справочников через `/api/options`;
- загрузка существующих карточек через `/api/cards`;
- поиск компании через `/api/company-search`;
- поиск ИНН на сайте через `/api/site-inn-search`;
- получение данных DaData через `/api/dadata-company`;
- сохранение карточки через `/api/cards`;
- подготовка выбора материалов через `/api/ai-selection`;
- финализация выбора через `/api/ai-selection/{selection_id}/finalize`;
- одобрение выбора через `/api/ai-selection/{selection_id}/approve`;
- запуск презентации через `/api/presentations`;
- опрос статуса через `/api/presentations/jobs/{job_id}`;
- загрузка истории через `/api/presentations/history`.

## 5. API endpoints

Публичная страница и статика:

- `GET /` - открыть интерфейс;
- `GET /styles.css` - стили;
- `GET /app.js` - frontend-скрипт.

Карточки и справочники:

- `GET /api/options` - справочники для формы;
- `GET /api/cards` - существующие карточки;
- `POST /api/cards` - сохранить или обновить карточку;
- `PATCH /api/cards/{row_number}/inn` - обновить ИНН в строке.

Поиск и обогащение:

- `GET /api/company-search?query=...` - поиск компании;
- `GET /api/site-inn-search?website=...` - поиск ИНН на сайте;
- `POST /api/dadata-company` - данные DaData по ИНН.

Выбор материалов:

- `POST /api/ai-selection` - подготовить выбор по правилам;
- `POST /api/ai-selection/{selection_id}/approve` - одобрить ручной или ИИ-выбор;
- `POST /api/ai-selection/{selection_id}/finalize` - отправить выбор в ИИ;
- `POST /api/ai-selection/{selection_id}/request-preview` - показать JSON запроса к ИИ.

Презентации:

- `POST /api/presentations` - запустить сборку;
- `GET /api/presentations/jobs/{job_id}` - статус сборки;
- `GET /api/presentations/history` - история сборок;
- `GET /api/presentations/{filename}` - скачать файл;
- `GET /photo/{filename}` - получить фото товара;
- `GET /api/image-preview?path=...` - предпросмотр изображения.

Битрикс24:

- `POST /api/bitrix/deal/webhook` - webhook для сделки;
- `POST /api/bitrix/lead/webhook` - webhook для лида;
- `POST /api/bitrix/webhook` - legacy webhook для сделки;
- `GET /api/bitrix/jobs/{job_id}` - статус задачи Битрикс24.

## 6. Переменные окружения

Основные переменные из `.env.example`:

- `OPENAI_API_KEY` - ключ OpenAI;
- `OPENAI_MODEL` - модель OpenAI, по умолчанию `gpt-4.1-mini`;
- `OPENAI_BASE_URL` - base URL OpenAI;
- `DEEPSEEK_API_KEY` - ключ DeepSeek;
- `DEEPSEEK_MODEL` - модель DeepSeek, по умолчанию `deepseek-chat`;
- `DEEPSEEK_BASE_URL` - base URL DeepSeek;
- `DADATA_API_KEY` - ключ DaData;
- `APP_STORAGE_MODE` - режим хранения, `excel` или `memory`;
- `BITRIX_WEBHOOK_URL` - входящий webhook Битрикс24 для API-вызовов;
- `BITRIX_INBOUND_TOKEN` - токен проверки входящих webhook в AutoCP;
- `PPTX_TO_PDF_CONVERTER` - путь к `soffice` или `libreoffice`;
- `ILOVEPDF_PUBLIC_KEY` - ключ iLovePDF;
- `ILOVEPDF_REGION` - регион iLovePDF, по умолчанию `eu`.

Если `APP_STORAGE_MODE` не задан, сервис использует `memory` на Render и `excel` локально.

## 7. Конфигурация ИИ

ИИ настраивается через `ai_config.json` или переменные окружения. Поддерживаются провайдеры:

- `openai`;
- `deepseek`;
- `rules` как fallback без внешнего ИИ.

Промпт берется из `mainprompt.md`. В промпте важно сохранено требование: вернуть только валидный JSON без markdown, комментариев и рассуждений.

Ожидаемый ответ ИИ:

```json
{
  "photo_ids": ["photo-1"],
  "review_ids": ["review-row-1"],
  "rationale": {
    "summary": "Краткое объяснение",
    "photos": "Почему выбраны фото",
    "reviews": "Почему выбраны отзывы"
  }
}
```

Сервис валидирует, что выбранные id есть среди кандидатов. Если ответ некорректный, используется нормализация или fallback на выбор по правилам.

## 8. Алгоритм выбора материалов

Первичный выбор выполняется в `build_payload_new.py` и `build_presentation_direct_new.py`.

Для отзывов используются признаки:

- категория товара;
- товарная группа;
- тип компании;
- ценовая категория;
- универсальность;
- релевантность текста.

Для фотографий сетей используются признаки:

- конкретные предпочитаемые сети;
- тип сети;
- регион;
- ценовой сегмент;
- категория товара;
- приоритет и score.

Финальный выбор может сделать пользователь или ИИ. Для ИИ передается не вся база, а ограниченный список кандидатов, чтобы ответ был контролируемым.

## 9. Генерация PPTX

Сборка PPTX выполняется через `build_presentation_direct_new.py`.

Основные операции:

- чтение payload;
- чтение selection override;
- поиск и нормализация изображений;
- выбор фотографий и логотипов;
- замена текстовых плейсхолдеров;
- замена image placeholders;
- добавление media-файлов внутрь pptx;
- обновление relationships и content types;
- проверка оставшихся плейсхолдеров.

Для PowerPoint-safe изображений используются проверки и конвертация. Это нужно, чтобы проблемные форматы не ломали презентацию.

## 10. Генерация PDF

Функция `_convert_pptx_to_pdf` в backend сначала пытается использовать iLovePDF, если задан `ILOVEPDF_PUBLIC_KEY`.

Если iLovePDF не настроен, сервис ищет локальный конвертер:

- `PPTX_TO_PDF_CONVERTER`;
- `soffice`;
- `libreoffice`.

Альтернативная генерация PDF напрямую реализована в `build_pdf_template_direct.py`. Она использует PyMuPDF и PDF-шаблон. По бизнес-схеме этот путь пока считается запасным, потому что качество результата ниже.

## 11. Интеграция с Битрикс24

Конфигурация Битрикс24 задается в `bitrix_config.json` и переменных окружения.

Основные функции:

- `_load_bitrix_config` - загрузка webhook URL и карт полей;
- `_verify_bitrix_inbound_token` - проверка входящего токена;
- `_bitrix_call` - вызов REST API Битрикс24;
- `_bitrix_get_deal_data` - чтение сделки;
- `_bitrix_get_lead_data` - чтение лида;
- `_bitrix_upload_file` - загрузка PDF в поле карточки;
- `_bitrix_move_deal_stage` - смена стадии сделки;
- `_run_bitrix_pipeline` - полный pipeline из Битрикс24.

Для сделок и лидов разные карты:

- `deal_field_map`;
- `lead_field_map`.

Поле файла задается ключом `presentationFileField`.

## 12. Pipeline Битрикс24

`_run_bitrix_pipeline` выполняет следующие шаги:

1. Ставит статус задачи `running`.
2. Загружает конфигурацию Битрикс24.
3. Получает данные лида или сделки.
4. Проверяет качество данных карточки.
5. Сохраняет карточку в Excel, если активен режим `excel`.
6. Делает dry run презентации для подготовки материалов.
7. Выбирает AI-провайдера.
8. Получает финальный selection от ИИ или fallback по правилам.
9. Запускает сборку презентации.
10. Проверяет, что PDF создан.
11. Загружает PDF в Битрикс24.
12. Для сделки меняет стадию.
13. Записывает результат в audit.

При ошибке задача получает статус `error`, ошибка пишется в лог и audit.

Контроль качества данных в автоматической ветке Битрикс24 реализован в `backend/app.py` перед dry run презентации. Проверка относится только к автоматическому pipeline из Битрикс24 и не применяется к ручному сценарию.

Если некорректны `companyName` или `productCategory`, например поле содержит `Ничего не подходит`, формирование презентации останавливается, задача Битрикс24 получает статус `error`, а в Render logs пишется запись с префиксом `[bitrix][data-quality] presentation stopped`.

Если некорректно опциональное поле, например `contactPosition`, `contactName`, `preferredNetworks`, `priceCategory`, `city`, `country`, `website`, `inn`, `companyType`, `productName` или `productDescription`, значение очищается и презентация продолжает собираться без него. Такая очистка пишется в Render logs с префиксом `[bitrix][data-quality] optional fields cleaned`.

Поля `productName` и `productDescription` не являются блокирующими: при их отсутствии или некорректном значении автоматическая презентация может быть собрана.

## 13. Хранение данных

Есть два режима хранения:

- `excel` - данные карточек сохраняются в XLSX;
- `memory` - данные не пишутся в Excel, используется для Render или временного режима.

Задачи презентаций сохраняются отдельно от режима хранения в `data/presentation_jobs`. Это позволяет видеть историю даже после завершения процесса.

Журнал `data/presentation_audit.jsonl` хранит краткие события:

- `PRESENTATION_DONE`;
- `PRESENTATION_ERROR`;
- `jobId`;
- компания;
- источник;
- имена файлов;
- ссылки скачивания;
- текст ошибки.

## 14. Безопасность

Сервис ограничивает доступ к локальным файлам через `_safe_root_file`: путь должен оставаться внутри корня проекта. Это важно для endpoint предпросмотра изображений.

Для входящих webhook из Битрикс24 используется `BITRIX_INBOUND_TOKEN`. Если переменная задана, запрос должен передать корректный токен.

API-ключи должны храниться в `.env` или production environment, а не в публичных файлах. Рабочие конфиги `ai_config.json`, `bitrix_config.json` и `.env` не должны попадать в публичный репозиторий.

## 15. Эксплуатационные риски

Основные риски:

- Render на бесплатном тарифе может засыпать;
- внешний API ИИ может быть недоступен;
- iLovePDF может быть недоступен или не настроен;
- локальный LibreOffice может отсутствовать;
- Битрикс24 webhook может прийти без нужного ID;
- маппинг полей Битрикс24 может устареть;
- шаблон презентации может содержать плейсхолдеры, для которых нет данных;
- изображения могут иметь формат, несовместимый с PowerPoint.

Для снижения рисков в сервисе есть fallback по правилам, журнал задач, проверка статусов и сохранение ошибок.

## 16. Что проверять при ошибках

Если презентация не собралась:

- посмотреть `/api/presentations/jobs/{job_id}`;
- проверить `data/presentation_jobs/{job_id}.json`;
- проверить `data/presentation_audit.jsonl`;
- проверить наличие шаблона PPTX;
- проверить наличие нужных изображений;
- проверить оставшиеся плейсхолдеры в отчете сборки.

Если не работает Битрикс24:

- проверить `BITRIX_WEBHOOK_URL`;
- проверить `BITRIX_INBOUND_TOKEN`;
- проверить `bitrix_config.json`;
- проверить, что webhook передает ID лида или сделки;
- проверить поле `presentationFileField`;
- проверить права входящего webhook Битрикс24.

Если не работает ИИ:

- проверить ключ `OPENAI_API_KEY` или `DEEPSEEK_API_KEY`;
- проверить base URL и модель;
- посмотреть JSON preview в интерфейсе;
- посмотреть сырой ответ ИИ;
- убедиться, что ответ содержит валидные `photo_ids` и `review_ids`.

Если не создается PDF:

- проверить `ILOVEPDF_PUBLIC_KEY`;
- проверить доступность iLovePDF;
- проверить наличие `soffice` или `libreoffice`;
- задать `PPTX_TO_PDF_CONVERTER`;
- проверить, что PPTX является валидным zip-пакетом.

## 17. Краткая карта процесса

1. LPtracker обзванивает поставщика.
2. Лид квалифицируется как заинтересованный.
3. Лид экспортируется в Битрикс24.
4. Робот Битрикс24 вызывает AutoCP.
5. AutoCP получает поля лида или сделки.
6. AutoCP подбирает материалы.
7. ИИ выбирает финальный комплект.
8. AutoCP собирает PPTX.
9. AutoCP конвертирует PPTX в PDF.
10. AutoCP загружает PDF в Битрикс24.
11. Битрикс24 отправляет презентацию клиенту.
12. Менеджер получает лид для дальнейшей работы.

## 18. Локальный запуск

Для локального запуска нужен Python и зависимости из `requirements.txt`.

Базовый запуск:

```powershell
python -m uvicorn backend.app:app --host 127.0.0.1 --port 8020
```

После запуска интерфейс открывается по адресу:

```text
http://127.0.0.1:8020
```

Если используется виртуальное окружение, лучше запускать Python из `.venv`. В проекте также есть `start_interface.ps1`, который предназначен для старта интерфейса на Windows.

Перед запуском желательно проверить наличие файлов:

- `Данные для разработки.xlsx`;
- `Каталог фотографий сетей.xlsx`;
- `Отзывы.xlsx`;
- `Список сетей.xlsx`;
- шаблон презентации;
- папки с изображениями.

Если часть XLSX-файлов отсутствует, backend при старте пытается скачать их по ссылкам из `data_sources.json`.

## 19. Размещение на Render

На Render сервис должен работать как FastAPI-приложение. В production-окружении нужно задать переменные:

- `BITRIX_WEBHOOK_URL`;
- `BITRIX_INBOUND_TOKEN`;
- `DEEPSEEK_API_KEY` или `OPENAI_API_KEY`;
- `DADATA_API_KEY`;
- `ILOVEPDF_PUBLIC_KEY`, если используется внешний PDF-конвертер;
- `APP_STORAGE_MODE=memory`, если запись в Excel на Render не нужна или невозможна.

По схеме процесса есть важное эксплуатационное замечание: бесплатный Render может засыпать. Если Битрикс24 отправит webhook в момент сна сервиса, запуск презентации может задержаться или сорваться. Для боевого процесса нужно либо держать сервис активным, либо использовать тариф/механизм, который исключает засыпание.

## 20. Детали работы с Excel

Backend читает и изменяет XLSX напрямую через XML-структуру Excel-файла. Это позволяет не зависеть от тяжелых библиотек для Excel.

Основные функции:

- `_xlsx_parts` - чтение частей XLSX как zip-пакета;
- `_shared_strings` - чтение shared strings;
- `_sheet_target` - поиск нужного листа;
- `_row_values` - получение значений строки;
- `_ensure_headers` - проверка и создание заголовков;
- `_save_card_row` - сохранение или обновление карточки;
- `_read_cards` - чтение карточек для интерфейса.

Такой подход требует аккуратности. Если структура Excel-файла сильно изменится, например будут переименованы листы или удалены ожидаемые заголовки, часть логики может перестать работать корректно.

## 21. DaData и поиск ИНН

В сервисе есть два способа работы с ИНН.

Первый способ - поиск компании по названию через открытый источник. Пользователь вводит название, сервис возвращает варианты компаний и позволяет выбрать подходящий ИНН.

Второй способ - поиск ИНН на сайте компании. Сервис нормализует URL, пробует несколько вариантов адреса, читает публичный текст страницы и извлекает возможные ИНН регулярным выражением.

После определения ИНН сервис может запросить DaData. Из DaData сохраняются:

- название;
- статус;
- юридический адрес;
- основной вид деятельности;
- среднесписочная численность;
- уставный капитал;
- реестр МСП;
- спецрежим налогообложения;
- доходы;
- расходы;
- недоимки;
- штрафы;
- руководитель.

Эти данные отображаются в интерфейсе и могут сохраняться в карточке.

## 22. Формирование запроса к ИИ

Запрос к ИИ состоит из системного промпта из `mainprompt.md` и пользовательского JSON. В JSON передаются:

- данные клиента;
- требуемое количество фотографий;
- требуемое количество отзывов;
- список кандидатов фотографий;
- список кандидатов отзывов.

Сервис специально передает ИИ ограниченный набор кандидатов. Это уменьшает риск нерелевантного выбора и исключает необходимость отдавать модели всю базу.

Перед отправкой можно посмотреть preview запроса через endpoint:

```text
POST /api/ai-selection/{selection_id}/request-preview
```

В интерфейсе этот preview показывается в блоке "JSON запроса в ИИ".

## 23. Обработка ответа ИИ

Ответ ИИ может прийти в разных форматах, поэтому backend содержит несколько защитных функций:

- извлечение JSON-объекта из текста;
- поиск первого сбалансированного JSON;
- сбор строковых фрагментов из ответа;
- проверка, похож ли объект на selection payload;
- нормализация выбранных id;
- объединение ответа ИИ с default selection.

Это нужно, потому что даже при строгом промпте модель может вернуть лишний текст или нестандартную оболочку. Основная задача backend - достать валидный выбор и не допустить подстановку несуществующих id.

Если ответ нельзя использовать, сервис сохраняет или возвращает ошибку, а в автоматическом сценарии может применить fallback на правила.

## 24. Selection lifecycle

Жизненный цикл выбора материалов:

1. Пользователь или pipeline вызывает `/api/ai-selection`.
2. Backend делает dry run презентации и формирует default selection.
3. Selection сохраняется во временном хранилище `AI_SELECTIONS`.
4. Пользователь может посмотреть кандидатов в интерфейсе.
5. Пользователь может изменить выбор вручную.
6. Пользователь может отправить выбор в ИИ через `/finalize`.
7. Backend получает финальный selection.
8. Пользователь одобряет selection через `/approve`.
9. При запуске презентации `/api/presentations` требует `approvedSelectionId`.

Это сделано, чтобы презентация не собиралась из непроверенного выбора.

## 25. Presentation job lifecycle

Жизненный цикл задачи презентации:

1. Endpoint `/api/presentations` проверяет компанию и approved selection.
2. Создается `job_id`.
3. В `PRESENTATION_JOBS` записывается статус `queued`.
4. Запускается background thread.
5. `_run_presentation_job` переводит задачу в `running`.
6. Выполняется сборка PPTX.
7. Если возможно, выполняется конвертация в PDF.
8. Если возможно, выполняется альтернативная сборка PDF по шаблону.
9. Статус становится `done` или `error`.
10. Задача сохраняется в `data/presentation_jobs`.
11. Результат пишется в `data/presentation_audit.jsonl`.

Frontend опрашивает задачу примерно раз в секунду и обновляет прогресс.

## 26. Bitrix job lifecycle

Жизненный цикл задачи из Битрикс24:

1. Битрикс24 вызывает webhook.
2. Backend проверяет токен.
3. Backend извлекает ID лида или сделки из query params, JSON body или form body.
4. Создается `bitrix_job_id`.
5. Запускается background thread `_run_bitrix_pipeline`.
6. Pipeline получает данные карточки из Битрикс24.
7. Pipeline формирует selection.
8. Pipeline запускает обычную задачу презентации.
9. Pipeline берет PDF из результата.
10. Pipeline загружает PDF обратно в Битрикс24.
11. Pipeline меняет стадию сделки, если сущность - deal.
12. Статус `BITRIX_JOBS` становится `done` или `error`.

Статус можно проверить через:

```text
GET /api/bitrix/jobs/{job_id}
```

Запрос требует тот же inbound token.

## 27. Маппинг полей Битрикс24

В `bitrix_config.example.json` описаны две карты:

- `deal_field_map`;
- `lead_field_map`.

Примеры внутренних полей AutoCP:

- `companyName`;
- `contactName`;
- `contactLastName`;
- `contactPosition`;
- `website`;
- `country`;
- `city`;
- `productName`;
- `productCategory`;
- `productNegotiationCategories`;
- `priceCategory`;
- `productDescription`;
- `preferredNetworks`;
- `conversationComment`;
- `region`;
- `presentationFileField`.

Для сделок часть данных может подтягиваться из связанных `COMPANY_ID` и `CONTACT_ID`. Для лидов данные берутся напрямую из полей лида.

Если поле `presentationFileField` не настроено или содержит заглушку, загрузка PDF в Битрикс24 завершится ошибкой.

## 28. Смена стадии сделки

В backend задана константа:

```text
BITRIX_AFTER_PRESENTATION_STAGE_ID = C148:FINAL_INVOICE
```

После успешной загрузки PDF для сделки вызывается `crm.deal.update`, и сделка переводится на этот этап. Для лидов аналогичная смена стадии в текущем коде не выполняется.

Если в Битрикс24 изменится воронка или ID стадии, эту константу нужно обновить.

## 29. Файлы результата

Результаты сборки сохраняются в корне проекта с именем, основанным на названии компании. Возможны файлы:

- `..._новый.pptx` - основная презентация;
- `..._новый.pdf` - PDF из PPTX;
- `..._pdf_template.pdf` - альтернативный PDF по шаблону.

Endpoint `/api/presentations/{filename}` отдает только файлы с допустимыми расширениями и безопасным именем. Это ограничение нужно, чтобы через API нельзя было скачать произвольный файл проекта.

## 30. Минимальный чеклист перед демонстрацией

Перед демонстрацией сервиса нужно проверить:

- backend запускается без ошибок;
- главная страница открывается;
- `/api/options` возвращает справочники;
- в интерфейсе видны существующие карточки;
- поиск ИНН работает или корректно сообщает об ошибке;
- DaData работает при заданном ключе;
- выбор материалов по правилам создается;
- JSON preview для ИИ формируется;
- ИИ возвращает валидный selection или fallback работает;
- PPTX собирается;
- PDF создается;
- история сборок обновляется;
- webhook Битрикс24 принимает тестовый запрос;
- PDF загружается в тестовую карточку Битрикс24.

## 31. Минимальный чеклист после изменения шаблона

После изменения PPTX-шаблона нужно проверить:

- все текстовые плейсхолдеры соответствуют ключам payload;
- image placeholders сохранили ожидаемые имена;
- размеры областей под изображения не сломаны;
- логотипы вставляются корректно;
- отзывы не выходят за границы блоков;
- длинные названия компаний помещаются на титульный слайд;
- итоговый PPTX открывается в PowerPoint;
- конвертация в PDF сохраняет внешний вид.

## 32. Минимальный чеклист после изменения промпта

После изменения `mainprompt.md` нужно проверить:

- модель возвращает только JSON;
- в ответе нет markdown;
- нет поля `reasoning_content`;
- количество `photo_ids` равно `required_photo_count`;
- количество `review_ids` равно `required_review_count`;
- все id существуют среди кандидатов;
- rationale короткий и пригоден для отображения в интерфейсе;
- при ошибочном ответе backend корректно сообщает проблему.
